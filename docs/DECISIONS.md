## 2026-07-08 — 데이터 소스: 스냅샷 JSON 소유 (B안)

**결정**: 외부 API를 런타임에 직접 호출하지 않고, 기존 소스에서 받아 정제한 뒤 **우리 저장소에 스냅샷(정적 JSON/상수)으로 소유**한다.

- **소스 역할 분담**
  - `PokéAPI` (pokeapi.co) — 본가 기준 불변 데이터(타입 상성, 도감 설명, 스프라이트, 정통 종족값). 안정적이나 챔피언스 고유값·최신 메타는 없음(전국도감 1025까지 커버, 갱신은 자원봉사 기반이라 지연).
  - `championsbattledata.com` — 챔피언스 전용 데이터(로스터 235종, 챔피언스 스탯/타입/특성, 사용률 통계). 단, 개인 팬이 운영하는 **집계층**이라 불안정.
- **원천 제작(A안)은 채택하지 않음**: 게임 데이터마이닝·인게임 사용률 직접 집계는 팬 사이트가 이미 하는 일을 재현하는 것이라 비효율. 우리는 "원천 제작"이 아니라 "정제 후 소유"만 한다.
- **데이터를 변동성 3등급으로 나눠 다르게 취급**
  - 불변(타입 상성표 18×18) → 코드 상수로 하드코딩(`src/lib/typeChart.ts`), fetch 불필요.
  - 느림(로스터·종족값·학습기) → 스냅샷 JSON. 게임 패치 때만 갱신.
  - 빠름(사용률·메타) → MVP에서는 보류. 다룰 경우 시즌 단위로 스냅샷 재생성.
- **구현 형태**: `scripts/`에 인제스트 스크립트를 두어 위 소스에서 받아 정규화 → `src/lib/data/*.json`으로 커밋. 런타임/빌드는 이 로컬 데이터만 읽는다.

**이유**: 포켓몬 챔피언스는 **공식 공개 API가 존재하지 않는다**(더 포켓몬 컴퍼니는 게임 데이터 API를 제공한 적 없음). 선택지가 전부 비공식이므로 어떤 소스든 끊길 수 있다. 이 서비스는 SSG(정적 페이지)와 북마크형 계산기라 데이터가 빌드 타임에 로컬에 있는 편이 유리하고, 대상 데이터가 거의 불변이라 런타임 API 의존의 이점이 없다. 스냅샷 소유는 팬 API 중단에도 사이트가 계속 동작하게 하고, 버전 관리·재현성·리뷰 가능성을 확보한다.

## 2026-07-08 — Next.js 채택 (Vite SPA 대신)

**결정**: 프레임워크로 Next.js 16 (App Router) 사용.

**이유**: 이 서비스는 "북마크해서 쓰는 계산기"이면서 동시에 검색 유입도 원한다.
유입은 검색(포켓몬별 정적 페이지, SSG), 재방문은 북마크(클라이언트 계산기)로 일어나므로
정적 생성과 SPA 경험을 한 프로젝트에서 해결할 수 있는 Next.js가 적합.
순수 도구였다면 Vite + React SPA로 충분했다.

## 2026-07-08 — 상태 관리: Zustand + TanStack Query 분리

**결정**: 서버 데이터(포켓몬 정보 등)는 TanStack Query, 클라이언트 상태(팀 구성, 계산기 입력)는 Zustand.

**이유**: 포켓몬 데이터는 거의 불변이라 Query 캐싱(staleTime 1시간)에 잘 맞고,
팀 구성 같은 UI 상태는 Zustand가 Redux 대비 보일러플레이트가 적다.
